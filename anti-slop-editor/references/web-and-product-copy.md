# Website, product, UI, SEO, and documentation copy

## Clarify the page's job

Distinguish conversion, editorial publishing, reference, portfolio/showcase,
account management, and support. Do not make a policy journal sound like a SaaS
landing page or a portfolio promise services it does not offer.

For an offer page, establish what it is, whom it serves, what someone can do,
what evidence supports the benefit, relevant limitations, and the next step.
Use only verified product capabilities and commercial terms. Never invent
customer counts, reviews, awards, logos, security certifications, response
times, guarantees, free trials, refund rights, or "no credit card required."

A short hero should orient the reader. The subheading can explain mechanism or
scope. The button should describe the real action. Do not force a slogan,
three benefit cards, an FAQ, or a call to action onto every section.

## Write useful search-facing content

Serve the actual query and reader need. Use descriptive titles, headings, link
text, and metadata that reflect the page. Include relevant terminology naturally;
do not repeat keywords, invent authority, promise rankings, or pad word counts.
Do not claim personal testing, experience, or editorial review that did not occur.

Treat a meta description as a truthful summary, not a new unsupported promise.
Keep structured-data text consistent with visible content. SEO is broader than
copy: this skill does not verify indexing, performance, schema, or rankings.
Google's people-first guidance is a supporting reference, not an endorsement of
this skill: https://developers.google.com/search/docs/fundamentals/creating-helpful-content

## UI and microcopy

Write the shortest text that still explains the state and action. Prefer
concrete labels such as "Save draft" to unspecified "Continue" where the result
would otherwise be unclear. Keep labels consistent across the product.

For errors, describe the known problem and the available recovery. Do not blame
the user or invent whether work was saved. For destructive actions, specify
what is affected and whether it can be recovered, only when known. For empty
states, explain what belongs there and the available first step.

Distinguish loading, success, failure, partial completion, and unknown status.
Do not use a cheerful success message for a pending action. Confirm constraints
such as character budgets without hiding crucial warnings to fit them.

Use accessible link and button names. Write alt text for the image's actual
purpose and content; never fabricate unseen details. Visual accessibility,
keyboard support, focus behavior, and responsive layout need separate testing.

## Documentation and code-adjacent prose

Explain behavior, prerequisites, consequences, and failure recovery where known.
Do not merely narrate syntax. Preserve exact API names, commands, flags, code,
versions, examples, and links unless changing them is explicitly in scope.
Keep changelogs version-scoped; ordinary reference pages should describe current
behavior rather than narrate an unseen diff. Do not alter code logic in an
anti-slop prose pass. Use the appropriate technical tools to validate examples.

## Original homepage example

Supplied facts: Draftroom is an editor for small editorial teams. It supports
shared drafts, review comments, and scheduled publication. No metrics supplied.

Headline: "Write, review, and schedule articles in one editor."
Supporting text: "Draftroom gives small editorial teams a shared place for drafts
and review comments, with scheduled publication when an article is ready."

Do not add "Publish 10x faster" or "Trusted by 5,000 teams." Both exceed the brief.
Do not invent a button destination; select a CTA only after the action is known.
